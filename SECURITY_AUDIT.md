# Аудит безопасности Telegram-бота (taro_bot)

Дата проверки: 2026-08-26
Стек: Go 1.24, `go-telegram/bot v1.23.0`, PostgreSQL (pgx), DeepSeek API (OpenAI-совместимый).

---

## 1. Безопасность токена и кода

### 1.1 Защита API-токена — ✅ (с оговорками)

| Проверка | Результат |
|---|---|
| Токен в исходниках | Нет. `BOT_TOKEN`, `AI_API_KEY`, `DATABASE_URL` читаются из `.env` / окружения (`internal/config/config.go:40-45`) |
| `.env` в `.gitignore` | Да, строки 2-3 |
| Утечка токена в логи | Нет. Библиотека `go-telegram/bot` v1.23.0 маскирует токен в ошибках: `raw_request.go:80` — `strings.Replace(netErr.URL, b.token, "***", -1)`. Подтверждено в `bot_run_err.log`: `.../bot***/getMe` — реальный токен в лог не попал |
| Токен в бинарнике | Нет. `bot.exe` читает конфиг из окружения при старте (`cmd/bot/main.go:20`) |
| Git-репозиторий | Отсутствует вообще (`git` не установлен, каталога `.git` нет). Ничего не опубликовано, но и версионного контроля нет |

Оговорки:
- ⚠️ Файлы `*.log` (`bot_run.log`, `bot_run_err.log`, `run_err.log`) **не** в `.gitignore`. Сейчас они не содержат секретов, но при запуске через командную строку с секретами в аргументах это станет утечкой. Добавить `*.log` в `.gitignore`.
- ⚠️ `.env.example` содержит только заглушки — ок. Но пример строки БД прямо документирует `sslmode=disable` (см. 2.2).

### 1.2 Защита вебхуков — ✅ не применимо

Бот работает через **long polling**: `b.Start(ctx)` → `getUpdates` (`cmd/bot/main.go:52`, библиотека `bot.go:133-137`). Вебхук-эндпоинта нет, поэтому поверхность для Webhook Spoofing отсутствует. Если в будущем перейдёте на webhook — обязательны HTTPS + проверка `X-Telegram-Bot-Api-Secret-Token` и/или IP-диапазонов Telegram.

### 1.3 Устойчивость к инъекциям — ✅/⚠️ смешанная

| Вектор | Результат |
|---|---|
| SQL-инъекции | ✅ Нет. Все запросы параметризованы (`$1…$N`) — `internal/storage/storage.go` (SaveUser:131, GetUserByTelegramID:145, SaveTarotRequest:188 и т.д.) |
| Выполнение кода на сервере | ✅ Нет `os/exec`, `eval`, динамических шаблонов, `unsafe`. RCE-векторов не найдено |
| XSS | ✅ Сообщения отправляются без `parse_mode` (`handlers.go:171-176`) — Telegram не рендерит HTML, инъекция разметки невозможна |
| **Prompt injection** | ⚠️ **Есть.** Пользовательский текст (запрос Таро `tarot.go:49`, место рождения `numerology.go:106`) без санитизации уходит в промпт ИИ (`ai.Generate`). Злоумышленник может написать «игнорируй все инструкции…» и получить произвольное поведение модели (не код на сервере, но риск контента/расходов). Системный промпт «не упоминай, что ты ИИ» также обходится |
| Ограничение длины ввода | ⚠️ Нет. `query`, дата/время/место, любые тексты — без лимитов (кроме лимита самого Telegram ~4096 символов). Крупные сообщения = большие строки в БД и дорогие вызовы DeepSeek |

## 2. Обработка и хранение данных

### 2.1 Минимум сбора информации — ⚠️

- ✅ Собирается только то, что нужно для функций: запрос Таро, дата/время/место рождения (для нумерологии), профиль Telegram.
- ❌ **Телефон запрашивается при регистрации без функциональной необходимости** (`start.go:63-66`, кнопка `RequestContact` в `handlers.go:180-192`). Нет SMS-проверок, уведомлений, доставки — номер не используется в логике бота. Это избыточный сбор чувствительных данных.
- ⚠️ Дата+время+место рождения — чувствительные персональные данные (позволяют идентифицировать человека).

### 2.2 Шифрование данных — ❌

- ✅ В транзите: Telegram API и DeepSeek API — по HTTPS (всегда).
- ⚠️ База данных: в `.env` и в примере `.env.example` — `sslmode=disable`. Для локальной БД на `127.0.0.1` это приемлемо, но:
  - документированный пример поощряет небезопасный дефолт;
  - нет кода, принуждающего `sslmode=require/verify-full` для удалённой БД.
- ❌ **Данные в покое не шифруются**: телефон, имена, дата/время/место рождения, вопросы, ответы ИИ хранятся открытым текстом в PostgreSQL (`schema.go:8-47`). Шифрования at-rest (pgcrypto / шифрование колонок / шифрованный диск) нет.

### 2.3 Соблюдение конфиденциальности — ❌

- ❌ Нет политики обработки персональных данных, нет экрана/команды согласия, нет `/privacy`, нет ссылки на политику.
- ❌ **Передача третьим лицам без уведомления**: данные пользователя (вопрос, дата рождения, место) отправляются в API DeepSeek (`ai.go:94-99`) — это передача ПДн третьей стороне, о которой пользователь не проинформирован и согласия не давал.
- ⚠️ Удаление данных: `tarot_requests` чистятся по TTL 48 ч (`main.go:57-75`, `storage.go:279-287`) — ✅. Но `users` и `numerology_requests` **не чистятся никогда** — ПДн накапливаются бессрочно. Механизма удаления данных по запросу пользователя нет.

## 3. Права доступа и логика работы

### 3.1 Ограничение прав (Rate Limiting) — ❌

- **Rate limiting отсутствует полностью**: ни на пользователя, ни глобального. Любой может слать сообщения без ограничений, инициировать расклады и нумерологии.
- ⚠️ Каждый запрос порождает горутину с таймером (`handlers.go:157-169`): расклад 1–3 мин, нумерология 1–2 ч. При спаме горутины накапливаются → нагрузка на память, БД и **финансовые расходы на DeepSeek API**.
- Рекомендация: per-user rate limiter (например, `golang.org/x/time/rate`), лимит длины сообщения, лимит одновременных активных запросов на пользователя.

### 3.2 Разграничение ролей — ⚠️

- ✅ Административных команд и панелей нет вообще — поверхности для атак на админ-функции нет (безопасно «отсутствием»).
- ⚠️ При появлении админ-функций должен использоваться allowlist верифицированных Telegram ID — в коде такой инфраструктуры нет.
- ⚠️ Платёжный гейтинг — заглушка: `payment.New(nil)` (`main.go:43`), `Service.Require` возвращает ошибку «not implemented yet» (`payment.go:89-97`). Сейчас бот в free mode — доступ ко всем функциям бесплатный.

### 3.3 Мониторинг активности — ⚠️

- ✅ Есть логирование ошибок (БД, ИИ, телеграм) и событий регистрации (`log.Printf` в `start.go:60-61`, `echo.go:103-104`).
- ⚠️ Нет: структурированных логов, логов подозрительной активности/попыток взлома, метрик, alerting. Rate-limit событий логировать нечего (лимитов нет).
- ⚠️ Логи содержат PII (`telegram_id`, `username`) — при передаче логов наружу это утечка ПДн.

## 4. Репутация и легитимность

### 4.1 Официальный статус — ⚠️ не проверяется из кода

- Код не содержит информации о верификации бота (синяя галочка у @BotFather — внешний фактор), нет `/help`, нет ссылки на политику конфиденциальности. Проверка наличия жалоб на спам/мошенничество — внешняя (BotFather, @BotSupport, t.me/...).

### 4.2 Безопасность платежей — ✅ не применимо (пока)

- Платёж **не реализован**: `PAYMENT_PROVIDER` пуст, провайдер `nil`, бот работает бесплатно. Внешних платёжных ссылок нет — риска мошеннических ссылок нет.
- При реализации: только официальные шлюзы (Telegram Payments / ЮKassa / Robokassa и т.п.), без самопальных ссылок. Обратите внимание: `requireFeature` (`handlers.go:139-141`) уже выводит `pay.PayURL` пользователю — при реализации убедиться, что URL формируется только провайдером.

## Приоритетные рекомендации

1. **Rate limiting** (критично): per-user лимит + лимит длины сообщения + лимит активных запросов.
2. **Политика конфиденциальности и согласие**: добавить `/privacy` и/или экран согласия; раскрыть передачу данных в DeepSeek; добавить удаление данных по запросу; TTL/очистка для `numerology_requests`.
3. **Убрать или сделать опциональным запрос телефона** — сейчас он не используется.
4. **Шифрование at-rest** для ПДн (минимум — телефон и дата рождения) или обоснованный отказ в политике; в `.env.example` поменять пример на `sslmode=require`.
5. **Prompt injection**: ограничить длину ввода, добавить в системный промпт инструкцию игнорировать попытки изменить поведение, рассмотреть санитизацию/экранирование пользовательского текста.
6. **`.gitignore`**: добавить `*.log`.
7. При переходе на webhook — HTTPS + секретный заголовок. При реализации оплаты — только официальные шлюзы.
